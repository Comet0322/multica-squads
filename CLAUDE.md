# multica-squads — what this project is

Config-as-code plus experiments for **Multica agent squads** on a self-hosted Multica (docker, `http://localhost:13654`, API `:18734`).
Question being answered: **can an agent squad reliably deliver complex software, and how should it be designed?**
Everything here is pushed to Multica with `./sync.py`; Multica itself is the upstream repo at `/mnt/a0df7f69-337a-4cb4-a10a-f48243e3ddfc/Code/multica` (do not put this config there).

## Layout
- `agents/<n>.json|.md` — agent config (`tier` → `tiers.json`) + instructions. `skills/<n>/SKILL.md`, `mcp/`, `squads/`, `properties/<n>.json` (workspace custom property definitions; admin-only to create, so they are config and agents only set values). v8's four: `Result` (PASS/REWORK), `Red SHA`, `Head SHA`, `Gate` (PR review / Decision needed / In flight). Retired configs live in `agents/archive/` and `properties/archive/` — `sync.py` globs only the top level, so archiving a file stops syncing it without deleting anything.
- `tiers.json` — model tiers: judgment (Opus 5.5 high: lead, test-writer, verifier), execution (Sonnet 5.5 medium: implementer), light (the docs stage).
- `sync.py [--dry-run] [--workspace X] [--only properties,skills,mcp,agents,squads]` — idempotent upsert by name, never deletes. Targets in `workspaces.json`; skips workspaces where you are not admin/owner.
- `tools/chat.py <agent> "<msg>" [--session ID]` — Multica CLI cannot send chat; this uses the REST API with the token in `~/.multica/config.json`.
- `tools/forgejo-pr.sh` — opens a PR on the local Forgejo (token from `forgejo/.env`).
- `forgejo/` — local Forgejo compose (UI `http://localhost:13000`, user `squadadmin`; secrets in gitignored `.env`, `.connection.json`).
- `docs/design-review.md` — **the criteria for auditing this squad's design without running it**: the wake inventory (every event has exactly one wake) plus W/O/R/S/C/E/$ items. Run it after every config change; `bench/failures.md` records what it caught.
- `bench/` — rubric, tasks, per-run scorer, aggregate report (see `bench/README.md`). Reliability metric is pass^n over at most 3 runs per variant (user cap), following tau-bench; no composite score.

## Current squad (`dev-team`, config v9 — written 2026-10-18, NOT yet verified)
v8 is banked at tag **`config-v8`** (sha `355946d`), the first config with a verified pass^3 (T3 3/3). v9 must earn its own pass^3 before any claim moves to it. What it changes:
1. **A spec now states two kinds of criterion.** `Acceptance criteria` (`AC1..ACn`) is behaviour that does **not** hold yet and must be watched failing; `Invariants` (`I1..In`) is behaviour that already holds and must not break, each carrying `Covered by:` — an existing check, or `nothing yet`. A `Covers:` line names an `I#` only when nothing covers it. This closes the self-contradiction that cost T3/v8-a2 a rework round (`bench/failures.md` F1).
2. **`qa.md`'s rule is now "a test that cannot fail is a bug"**, with two proofs: an `AC#` fails now, an `I#` fails under a discarded throwaway mutation. An `AC#` that already holds is reported as a spec defect, never tested.
3. **The verifier checks commit authorship** (`reviewer.md` §4 check 6) and `handoff-protocol` now tells each agent to commit as itself (`sq-qa <sq-qa@multica.local>`), which is what the runtime already did for 24 of v8's 28 commits — pinning `squadbot` had 0/28 compliance.
4. **The merge-capable Forgejo credential is out of the file the squad sources.** `forgejo/.env` holds only `FORGEJO_TOKEN` (squadbot, cannot merge); the admin password and token moved to `forgejo/.env.admin`. On a local daemon running as the same user this stops the accidental path, not a determined one — see the open item.
5. **Evidence is decided by the tree, not by the criterion's letter** (ADR 0003). The AC/invariant split stays for *who owes work*, but which evidence a test owes is one mechanical question — is the behaviour present where the test runs? — with red and **mutation** evidence as co-equal forms. This is what actually closes F1: keyed on the letter, a reopened test stage, an AC an earlier ticket delivered, and every invariant all demand a red run that cannot exist.
6. **Two audit rounds of four agents each, applied as structural fixes** rather than per-instance patches. The load-bearing ones: every owner wake must first decide whether it is a *reconcile* wake (state, never timestamps — the barrier re-fires on any child status change, and a leader with no stop re-ran its own decision table and could create every ticket twice); the verifier claims a ticket **before** promoting its first stage, and the leader never restarts a `todo` ticket that has children (both leave a parent in `backlog`, which loses the barrier permanently); every promote is **two** writes, because a stage whose run finished after being reset sits in `done`; a `**Relay**` comment on the spec is the one path from a member to the leader when a person comments on a handoff; a PR-feedback ticket is **promoted**, not just created; `Stop` cancels **top down**, because cancelling upwards fires a barrier on each still-open parent and restarts the work the human just stopped; each member first checks whether its wake is a re-dispatch of work it already pushed; and the verifier's verdict is a `**Report**` on the ticket, which is the only artefact the leader can read and the source of the PR body's per-criterion table.
   Also: `Repo` is a spec section (the clone URL and repo name existed in no file an agent could read), tickets carry `Base:`, the brief's `cycle N` label is per-issue and monotonic while the rework *budget* is per-ticket and resets on human input, the formatter standard is "no new violations against the `Repo intake` baseline" rather than "clean", a retired criterion is a `Retires:` line (the only thing that authorises deleting a test), and `definition-of-done` no longer states the pre-v9 red-only rule to four agents at once.

## Previous squad (`dev-team`, config v8 — tag `config-v8`, **verified: T3 pass^3**)
Leader `sq-lead` + `sq-reviewer`, `sq-qa`, `sq-implementer`, `sq-doc` — **the v7 names, kept on purpose**: nothing is created or archived on the platform, squad membership does not churn, run attribution stays continuous, and `bench/score.py`'s agent-name logic keeps working. What changed is the jobs: `sq-qa` writes the tests **before** the code (tier execution → judgment) and `sq-doc` is each ticket's last stage. `squad-medic`/`pr-watch` were already gone in v7 (ADR 0001).
Vocabulary is in `GLOSSARY.md`. Design rationale: `docs/adr/0002-tests-first-written-by-another-agent.md`. Audit standard: `docs/design-review.md`.

**Test-first, and the tests are written by an agent that never sees the implementation.** That is the whole independence mechanism — there is no post-hoc QA pass.

```
spec                    squad → sq-lead      frozen after approval; corrections are comments
├ stage 1  spec-check   sq-reviewer
├ stage 2  ticket F1    sq-reviewer          verification happens here, in the owner's barrier wake
│  ├ stage 1  test      sq-qa                red: tests that fail for the right reason
│  ├ stage 2  implement sq-implementer       green, nothing else
│  └ stage 3  docs      sq-doc               documentation files only
└ stage 3  ticket F2    ...
```

- **Every ticket has the same three stages.** No ticket shapes, no `Deliver` ticket, no fast path. Docs is **last** because it commits to the same branch: the head a human merges must be a head that was verified.
- **`done` is the only verb a member has.** No `@mention`, no `blocked`, no comment on an issue it does not own. An agent that cannot finish the work still finishes the issue and says why.
- **Nothing copies the acceptance criteria.** Tickets carry `Covers: AC#` only; everyone reads the text from the spec (description + every `**Spec correction**`, newest in force), so there is no copy to go stale.
- **The verifier judges the tests against the spec, not the ticket** — which is also how a ticket citing a nonexistent AC gets caught.
- Stage 1 closed: each AC has a test, and re-running at `Red SHA` **fails for the right reason** (an assertion, not a compile error). Stage 2 closed (the full check): tests pass, suite green, `git diff --numstat <Red SHA>..<Head SHA>` shows **0 deleted test lines**, diff scope allowed; the last ticket's stage 2 is also the integration check, there is no separate one. Stage 3 closed (cheap): documentation files only, suite still green.
- **Rework is counted, not stored**: the owner counts its own `**Brief (cycle N)**` comments — **not** `done → backlog` transitions, which over-count because reopening one stage resets the stages above it. At two it stops, sets the ticket `Result = REWORK` and closes it; the leader then sets `Gate = Decision needed` and the spec `in_review`. The human is the only escalation target.
- The leader's entire logic is a four-row table on `(which child closed, its Result)`; the PR is opened by the leader as the terminal step, never by a stage.
- PR feedback is a comment on the spec → an ordinary new ticket → it becomes the last ticket, so its own verification is the integration check on the head the human merges. Nothing is reopened.
- **Nothing runs on a timer.** Every owner wake re-checks its own level first (`in_review` with a report → `done`; `todo`/`in_progress` with no active run → restart with two writes; anything moving → leave it). A stall where nothing completes is a failure and is recorded as one.
- Every issue the lead creates gets label `run-<YYYYMMDD>-<slug>`.
- **Verified at v8.** Four probes passed, then T3 three times hands-off: 3/3, pass^3, 0 interventions, 0 stalls (ADR 0002, Validation — result).
- **The owner's self-recovery is weaker than it reads, and the window is wider than "a ticket's first stage".** The general rule is that **no wake arrives between a run's first non-status write and its next status write**: a comment, a property and a description edit all start nothing. So every ticket-closing exit (report, three properties, then `done`), the rework decision (report, brief, `Result`, then the reset), the brief row (claim, report, then the reset), and the leader's spec-check rows (correction, brief, then the restart) each carry a window in which a death is unrecoverable — and `reviewer.md` §0 steps 6 and 7 and `lead.md`'s backlog-promote row, which are written for exactly those states, are reachable only if some other event supplies a wake. This is still ADR 0001's accepted position with 0 occurrences in 211 runs, and the mitigation is the same (`watch.py`'s `STALLED`), but the scope below understates it.
  **The first-stage case specifically:** An owner re-checks its level only *on a wake*. After promoting stage 2 or 3 it gets one free: the promotion is itself a child status change while a lower stage is terminal, so the barrier re-fires within seconds. After promoting a ticket's **stage 1**, or the spec-check, no stage is terminal yet, so no barrier can fire and **no further wake arrives at all** — a first stage that ends its run leaving its own issue non-terminal is an unrecoverable stall with the human as the only recovery path (ADR 0001's accepted position; `docs/design-review.md` R3b). 0 occurrences in 211 runs, and `watch.py`'s `STALLED` is the detector.

## Hard-won facts (verified unless marked)
- Squad assignment/@mention wakes **only the leader**; members run only when assigned/@mentioned. Squad `instructions` go to the leader only. `role` is a roster label.
- **A repository whose tests fail on `main` is outside the capability boundary**, for the same reason as one with no tests: review and QA have no baseline and the squad cannot tell its own regressions from the pre-existing ones. The boundary must be *established by running*, not inferred by reading — the same rule that already applies to a bug's Reproduction. What makes this happen rather than being skipped is that another agent rejects the spec without it (`reviewer.md` spec check 3, which requires the intake rows to *pass* and not merely to match a fresh run), not that the leader is asked nicely. An **empty** repository is the one carve-out, in both `lead.md` and `repo-intake`: nothing to build means no baseline to protect.
- **Platform default says delivered → `in_review`, `done` stays human.** Stage barriers only fire on `done`/`cancelled`. Agent instructions outrank the platform workflow ("Instruction Precedence"), but a *skill* does not, so the status override lives in each agent's own `.md`. Leader also self-heals sub-issues stuck in `in_review`.
- Chat (leader) sees repos only if registered: `multica repo add <url>`; then `multica repo checkout <url>` gives a worktree. Daemon clones need credentials (`~/.git-credentials` has the Forgejo entry). Workspace repo list: kv-cli on Forgejo.
- Forgejo reachable by Multica backend as `http://forgejo:3000` (shared docker network `multica_default`); webhook target must be `http://backend:8080/api/webhooks/vcs/<connection-id>`, not the localhost URL the UI shows. Forgejo needs `webhook.ALLOWED_HOST_LIST=*`.
- Timeline entries carry `actor_type` (agent/member) → interventions are measurable; runs carry `usage` (array per model), `is_leader_task`.
- **`attribution.source` is NOT "who started this run"** — it names the human or agent at the root of the causal chain, so it is useless on its own (measured table in `bench/failures.md`). A platform stage barrier reports `delegation` in an agent-built family but `direct_human` in a hand-built one; a person firing a rule by hand reports **`trigger_owner`**. What actually discriminates: `wakeup_system_rule` non-null = a platform rule fired; `attribution.delegated_from_task_id` present = another agent's task caused it; neither = a person (in v6 also an `sq-medic` restart, which the scorer still pairs with its `**Medic**` comment so pre-v7 runs stay scoreable; v7 has no such actor). `usage` is **summed over every request in a run**, so `cache_read_tokens` = context size x request count and is NOT a context peak: B1's 1,207,032-cache-read run had accumulated only **59,797** tokens of context, re-read ~20 times. `cache_write_tokens` is the context actually accumulated (B1 max 62,953 over 74 runs, leader median 10,631), and is the D-tier metric. The v4 "1.23M context peak" was the same misreading.
- **Platform stage barriers are reliable; v4's missed wake was not a barrier.** Setting a child `done` fires `child_done` on the parent within ~20 s, and `issue update --no-start` suppresses the run on the issue being updated but **not** the parent's barrier. v4's un-woken leader came from an **agent-created** wakeup rule that the platform rate-paused; v6 creates no such rules (v5 families have zero and their barriers fired).
- **A `child_done` barrier wakes the parent issue's assignee even when that is an individual agent, not a squad** (probe F18, 2026-10-17: parent ACHE-144 assigned to `sq-reviewer`, child set `done` 14:04:39 → a `sq-reviewer` run the same second, `wakeup_system_rule: child_done`, `is_leader_task: None`). Only *squad* assignment is leader-only. This is what makes per-level ownership possible; v6 woke the leader on every stage only because every ticket was squad-assigned.
- **Custom properties give a closed, normalized vocabulary — the one guarantee prose cannot** (probe F21). `multica property create --type select` then `issue property set <id> --name "QA verdict" --value "PASS"`: an invented value is rejected with the valid list, a case variant is normalized to the canonical name, and `issue property list <id>` returns `name` + `display` resolved (`issue get` keys them by UUID, so use the list form). Definitions are owner/admin only, so they live in `properties/*.json` and `sync.py` creates them; agents only set values. **Property changes do NOT appear in the timeline**, so a property is the authoritative *final* state and can never count cycles.
- **The platform's duplicate guard is defeated by paraphrase** (probe F20): an identical title is rejected (`Active duplicate issue exists: …; use --allow-duplicate`), but one extra word in the title creates silently — exactly the ACHE-125/127 shape. A guarantee against duplicates has to be semantic ("compare by what the issue is FOR"), which is why it lives in the instruction.
- **`status_changed` timeline entries carry `details.from`/`details.to`**, so the rework count is structural. But the shape changed with the two-write restart: pre-v7 sent work back as a single `done` → `todo`, while v7 and v8 must go `done` → `backlog` → `todo`. Counting every `done` → `backlog` over-counts, because reopening stage 1 also resets the stages above it and the owner then promotes those normally — so each one is paired with the `**Brief (cycle N)**` comment that follows it, which the instructions put on the reopened stage only. The legacy prose counts (`review_changes_requested`, `qa_fail`) match the phrase anywhere in a comment and over-count when a later comment quotes a verdict (B1: 2 real verdicts counted as 3); they are kept only for pre-v7 comparability.
- **A stage barrier wakes the owner but does NOT promote the next stage** (probe F19, 2026-10-17: stage 1 `done` fired one `child_done` run on the parent while the stage-2 child stayed `backlog` for 75 s). So Multica has no "unblock and let a free worker claim it" model — coordination here is push (wake the owner, the owner promotes), never pull. This is why the squad cannot adopt Claude Code Agent Teams' dependency-unblock-plus-self-claim pattern; it is a platform limit, not a design choice.
- **The platform already reconciles dead runs; the squad must not.** A server-side sweeper runs every **30 s** (`runtime_sweeper.go`: `sweepInterval`) and fails tasks stuck in `dispatched` past `dispatchTimeoutSeconds = 300` or in `running` past `runningTimeoutSeconds = 9000` — but the running wall clock is **AND-gated by daemon liveness**, so a task whose runtime still heartbeats (`RuntimeClaimFreshnessSeconds = 150`) is never killed by it, which is what lets multi-hour runs survive. `defaultRuntimeReconnectGrace = 3h` keeps local work alive through a partition. Then `HandleFailedTasks` (`service/task.go:5998`) does three things in order: `MaybeRetryFailedTask` auto-retries with an attempt ceiling and backoff but **only for `retryableReasons`**, which deliberately excludes agent-side errors ("those are real problems that the user should see, not infrastructure flakiness"; the one exception is `provider_network`); then `recoverDelegatedTaskFailure`; then, if the issue is `in_progress` with no active task and no retry queued, it **resets the issue to `todo`** — excluding `in_review` and `blocked` "because a human or an external dependency owns the issue then", which matches this squad's design exactly.
  So infrastructure failure is fully covered by the platform, and agent-side failure is a *deliberately visible* stall with the human as the recovery path (ADR 0001's position, reached independently). **The only uncovered case is a run that ends `completed` while leaving its own issue non-terminal**: nothing is broken from the platform's view, so no sweeper sees it. That is an instruction-compliance risk, not an infrastructure one — 0 occurrences in 211 measured runs — and it is the same class as v4's `wakeup_paused` death (an agent-created rule being rate-paused is not a task failure either). The right tool for it is the detector we already have (`watch.py` prints `STALLED`, `score.py` records `stalled_sub_issues`), not a resync: a resync would convert the one signal that locates a missing wake into a silent recovery.
  Operational corollary: a daemon that dies mid-run takes **up to 3 hours** to surface as a failed task, so never wait on the platform to mark a benchmark run failed — `watch.py`'s 12-minute stall detection is the faster and more useful signal.
- **A run starts on an issue in exactly three ways** (`service/issue_trigger.go:126-141`, the single predicate both write paths use): it is **created** in a status other than `backlog`, its **assignee changes** while it is not `backlog`, or its status moves **out of `backlog`** into something that is not `done`/`cancelled`. Nothing else does — **`done → todo` and `blocked → todo` start nothing**, and `multica issue status` prints "status changed to todo" either way, so the board looks correct with nobody working. An agent's comment on an issue assigned to another *agent* also starts nothing unless it carries a `mention://` link; on the **squad**-assigned spec issue any agent comment wakes the leader. Therefore: every start or restart is two writes, `status <id> backlog` then `status <id> todo`, and the only cross-agent wake is the roster mention form `[@Name](mention://agent/<id>)` — a plain `@name` is dead text (`util/mention.go:16`). Probe F18-2's "reopening re-fires the barrier" is true and was NOT evidence for this: `ACHE-145` had no assignee and zero runs ever.
- **A human's comment DOES wake an agent-assigned issue's assignee** (probe v8-P2, 2026-10-18: a member report posted on `ACHE-174` at 18:39:56 started an `sq-qa` run the same second, `attribution.evidence.kind: comment`). Only an *agent's* comment on an agent-assigned issue wakes nobody. So a person commenting on a handoff reaches that member directly, bypassing the owner — which is why PR feedback is defined to go on the spec issue, and why a hand-built probe that plants a report pays for one extra run.
- **A restart is queued, not dropped, when a run is already in flight on the same (issue, agent).** Same probe: the owner's two-write restart at 18:40:31 landed while a run was active, and the new run started at 18:40:44, the instant that one finished. `HasPendingTaskForIssueAndAgent` deduplicates a *pending* task, it does not discard a promotion.
- **`multica issue runs <id> --siblings` is rooted at the issue's PARENT**: it returns that parent plus every child of it — i.e. the issue and its siblings, active only, capped at 20. It does **not** reach grandchildren, so rooted at the spec it cannot see a handoff. To see one ticket's handoffs, root it at one of them.
- **`multica issue children <id>` returns one entry per stage with `total` and `done` counts** (plus the issues), so the layout is one call — but **never derive *which* stage just finished from those counts**: after any reopen the counts can show two stages complete, and the owner then reads a stale verdict and reworks forever. The barrier's own system comment already says it: `Stage N of this issue is complete — its last sub-issue [ID] … Stage progress — Stage 1: 1/1 done; Stage 2: 0/1 done (next)` (`handler/issue_child_done.go:366` + `stageProgressSummary`). Read the newest comment on the issue that woke you; it also distinguishes a barrier wake from a human comment and from an escalation. Its trailing advice to set the parent `in_review` contradicts this squad's status override, which wins.
- **Terminal means `done` or `cancelled`, and nothing else** (`handler/issue_child_done.go:99`, `isTerminalChildStatus`). `blocked` fires **no** barrier, so `blocked` alone is a permanent stall in a squad with no medic: escalation is an @mention comment first, then `blocked`. The mention wakes the mentioned agent even on an issue it is not assigned (B1: the implementer's report mentioned `sq-lead`, which ran at 12:36:25 on `ACHE-122`).
- **Wake deduplication is per (issue, agent)** (`HasPendingTaskForIssueAndAgent`, same file `:914`, keyed on the reviewed head SHA), so a report that @mentions its owner and the barrier that follows are **two runs on two different issues**: measured 12:36:25 on the child and 12:36:26 on the parent. **17 of B1's 74 runs were woken by a comment**, against 27 barrier wakes and 30 promotions (`attribution.evidence.kind`) — roughly a quarter of the cost, and in v7 the owner's wake promotes stages, so the duplicate can promote twice. Reports therefore @mention nobody.
- **The `child_done` barrier rule has no memory of having fired.** It is a single `mode: continuous` event rule on `issue.status_changed` with condition `{children_done, each_stage: true}`, so it re-evaluates on **any** child status change and wakes the owner again whenever some stage is fully terminal. Promoting the next stage is itself such a change, so **every stage transition costs one extra owner wake for the stage that just closed** (T3/v7-a1: stage-1 barrier re-fired at 16:32:24, the instant F1 went `backlog → todo`; the second leader run returned `no_action`). This is structural, not a defect, and the only defence is that every owner wake re-checks its own level before advancing anything. **Unreconciled with the code, 2026-10-18:** `handler/issue_child_done.go` guards its notification path with `if prevTerminal || !nowTerminal { return }`, i.e. it fires only on a child going non-terminal → terminal, and grepping the Go source for `children_done` finds no such wakeup rule at all — so the mechanism above is the measured behaviour (v7-a1) and the one below is the code as read. Neither was overwritten because the design is safe either way: the owner re-checks its level on every wake, so an extra wake costs a `no_action` run and a missing one is covered by the next real child transition.
- **The barrier closes only when every stage ≤ the completing child's stage is terminal** (`stageBarrierClosed`, same file `:571`), so a stage that completes while a lower stage is still open wakes nobody. Promote one stage (and one ticket) at a time.
- **A parent in `backlog`, `done` or `cancelled`, or assigned to a human, gets no child-done notification at all** (same file `:118`-`:131`). Never leave work running under a parent in one of those states — which is also why a reopened ticket must leave `done` before its children restart.
- **Creating an issue in any status other than `backlog` starts a run on its assignee immediately**, and `issue create` has no `--no-start` (only `issue status`/`issue update` do). Measured: `ACHE-114` created `in_progress` at 12:32:14 started a leader run that logged `squad_leader_evaluated: no_action — "Assignment wake on spec creation; chat run already…"`, while `ACHE-115` created `backlog` at 12:32:25 started nothing and ran only when promoted at 12:32:48. So every issue is created `backlog` and moved afterwards.
- **Reopening a completed stage and completing it again re-fires the barrier** (same probe: child back to `todo`, then `done` again at 14:06:21 → a second `child_done` run within 15 s). So rework can be a status change instead of a new issue. `--stage` groups children into an ordered barrier group and the CLI states the parent assignee is woken only when *every* sub-issue in a stage finishes.
- **Concurrent leader runs are normal and harmless when they are on different issues.** B1 had 12 overlapping `sq-lead` run pairs (`max_concurrent_tasks: 3`), every one of them a spec run overlapping a ticket run during a pipelined handoff; two runs on the *same* issue never overlapped. B1's duplicate rework (`ACHE-127`) was **one run repeating its own create 25 s apart**, not a concurrency race — and the duplicate was acted on, costing a stray commit and an extra rework round (`bench/failures.md` 2026-10-17).
- **A comment on a squad-assigned issue wakes the leader by itself**, so commenting and then restarting or `rerun`-ing the same issue wakes it twice, 30 s apart — two leaders on the same state can promote a stage or open a rework twice (probe F17-2). This is why only the leader comments on the spec issue, and why a comment on an agent-assigned handoff — which wakes nobody — can safely be paired with a restart.
- `multica issue wakeup create` needs an explicit `--agent-id` when a person runs it (it defaults to the authenticated *agent*), and event names are dotted (`comment.created`, not `issue_commented`); `multica issue wakeup events` lists them.
- `multica issue runs <id> --active` answers "is an agent working right now", `--siblings` widens it to the issue's **parent plus that parent's children** (see the fact above: siblings, not descendants). `multica issue rerun <id>` re-enqueues the current assignment and does not depend on wakeup rules (what v6's sq-medic used; v7's instructions never call it, because the two-write restart is the one mechanism verified from inside an agent); `multica issue wakeup trigger` is the manual fire, and `manual` fires bypass the rate pause (`issue_wakeup.go:1292`).
- The VCS webhook models only `pull_request` and `ci_status` (`vcs_webhook.go:139`); **PR comments never reach Multica through it**, so the PR-comment relay polls the Forgejo API instead (`tools/forgejo-pr-comments.sh`). CI status *is* modelled, so Forgejo Actions would mirror onto the PR without extra wiring.
- **A `multica repo checkout` worktree shares the repository's `.git/config`, so an agent commits with whatever identity is configured there.** Measured 2026-10-18: `kv-bugs` and `kv-cli` carry `user.email=jerrymark611@gmail.com` locally, and `fix/kv-bugs-v7-a1`'s F1 commit `8bf98b7` — the `Head SHA` of handoff `ACHE-158`, written by `sq-implementer` — is authored `Comet0322 <jerrymark611@gmail.com>`. Where the config had no name, the runtime filled in `<agent>@multica.local`, and the same `sq-doc` appears as `@noreply.invalid` on one branch and `@multica.local` on another. An agent commit carrying a person's identity makes a hands-off run look like it was not, so `handoff-protocol` pins `git -c user.name=squadbot -c user.email=squadbot@localhost` with a `Co-Authored-By` trailer naming the agent. Never `git config` in a checkout: a worktree write lands in the shared config. **That pin does not work.** Across T3/v8's 28 commits, zero are `squadbot <squadbot@localhost>`: 24 are `sq-<name>@multica.local` and four are something else again, including `Comet0322 <jerrymark611@gmail.com>` on a3 and `multica-squad <jerrymark611@gmail.com>` on a2 — so the human's address still reaches 2 of 3 scored branches. The runtime fills the identity in and prose does not stop it; enforcing it needs a check on the result (`git log --format='%ae' <Red SHA>..<Head SHA>` in `reviewer.md` §4) rather than an instruction to the author (`bench/failures.md` F2).
- **Which Forgejo account a PR comes from is a convention, not a constraint.** `tools/forgejo-pr.sh` always authenticates with `FORGEJO_TOKEN` (squadbot), but `forgejo/.env` also holds `FORGEJO_ADMIN_TOKEN` and nothing stops an agent reading it: T3/v8-a3 opened PR #8 as **`squadadmin`** while a1 and a2 opened #6 and #7 as `squadbot`. Since `main` is protected so that only `squadadmin` may merge, a run holding that token could merge its own PR. The gate held in all three runs, but it is not enforced (`bench/failures.md` F3).
- **A black-box hidden-test file shares a package namespace with the tests under test**, so every identifier in it must be prefixed. T3/v8-a3 declared its own `parallel` helper, collided with the hidden file's, and the package failed to build — measured as 0% hidden rather than as an error. Fixed in `ac2ea96`; the renamed harness still reproduces the documented baseline exactly (4 fail / 2 pass on `bench-base-t3`).
- Agents push as **`squadbot`** (credential in `~/.git-credentials`, token also in `forgejo/.env` as `FORGEJO_TOKEN`; the admin token is kept as `FORGEJO_ADMIN_TOKEN`). `main` is protected on `kv-cli` and `kv-bugs`: direct push is rejected by the server and only `squadadmin` may merge. Verified for real, not by reading settings.
