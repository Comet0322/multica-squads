# multica-squads — what this project is

Config-as-code plus experiments for **Multica agent squads** on a self-hosted Multica (docker, `http://localhost:13654`, API `:18734`).
Question being answered: **can an agent squad reliably deliver complex software, and how should it be designed?**
Everything here is pushed to Multica with `./sync.py`; Multica itself is the upstream repo at `/mnt/a0df7f69-337a-4cb4-a10a-f48243e3ddfc/Code/multica` (do not put this config there).

## Layout
- `agents/<n>.json|.md` — agent config (`tier` → `tiers.json`) + instructions. `skills/<n>/SKILL.md`, `mcp/`, `squads/`, `properties/<n>.json` (workspace custom property definitions; admin-only to create, so they are config and agents only set values).
- `tiers.json` — model tiers: judgment (Opus 5.5 high: lead, reviewer), execution (Sonnet 5.5 medium: implementer, qa), light (Haiku 5.5: doc, watcher).
- `sync.py [--dry-run] [--workspace X] [--only properties,skills,mcp,agents,squads]` — idempotent upsert by name, never deletes. Targets in `workspaces.json`; skips workspaces where you are not admin/owner.
- `tools/chat.py <agent> "<msg>" [--session ID]` — Multica CLI cannot send chat; this uses the REST API with the token in `~/.multica/config.json`.
- `tools/forgejo-pr.sh` — opens a PR on the local Forgejo (token from `forgejo/.env`).
- `forgejo/` — local Forgejo compose (UI `http://localhost:13000`, user `squadadmin`; secrets in gitignored `.env`, `.connection.json`).
- `docs/design-review.md` — **the criteria for auditing this squad's design without running it**: the wake inventory (every event has exactly one wake) plus W/O/R/S/C/E/$ items. Run it after every config change; `bench/failures.md` records what it caught.
- `bench/` — rubric, tasks, per-run scorer, aggregate report (see `bench/README.md`). Reliability metric is pass^n over at most 3 runs per variant (user cap), following tau-bench; no composite score.

## Current squad (`dev-team`, config v7)
Leader `sq-lead` + `sq-implementer`, `sq-reviewer`, `sq-qa`, `sq-doc`. **No utility agents and no autopilots**: `squad-medic` and `pr-watch` were deleted and `sq-medic`/`sq-watcher` archived in v7 (see `docs/adr/0001-ownership-per-level-no-autopilot.md`).
Vocabulary is in `GLOSSARY.md` (scenario vs task, scope tiers A/B/C/D, scored run vs deterministic probe, intervention vs recovery). v6 scope carried into v7: A (scored) = feature-add + symptom bug; B (mechanism, verified once) = greenfield **(verified, B1)**, PR-comment relay **(replaced: the human comments on the spec issue)**, fast path **(traced only, NOT run)**; C (must be refused in chat) = 12 scenarios incl. UI, performance, migrations, multi-repo, hotfix; D (measured only) = context peaks.
**Ownership is per level and a stage barrier delivers the handoff.** The spec belongs to `sq-lead`, each ticket to `sq-reviewer`, each handoff to its assignee; finishing your own issue wakes the owner above you. Members never mention a peer and never change another issue's status.
Flow: user chats with sq-lead → lead runs the **repo-intake** skill on every repo involved (build, `go test` on `main`, formatter/vet baseline, an `AGENTS.md`/`CLAUDE.md` to take conventions from, `.gitignore`, dependencies, and whether squadbot can push) and pastes the output into the spec's `Repo intake` section → lead checks the **capability boundary** and refuses out-of-scope work in chat without creating issues → one spec at a time → spec + ticket plan approved in chat → spec issue (frozen, assigned to the squad) with a stage-1 `spec-check` handoff (sq-reviewer: ACs testable, Impact-analysis symbols exist, a bug's Reproduction reproduces, and the `Repo intake` evidence is real — it re-runs the build and the test suite on `main` itself) → feature tickets F1..Fn in stages, **each assigned to sq-reviewer**, whose children are only stage 1 implement (sq-implementer) and stage 2 qa (sq-qa) — the review happens in the owner's own barrier wake, on the ticket → final `Deliver` ticket: integration QA → docs → open PR → spec `in_review` at the PR (the only human gate) → user merges → Forgejo webhook sets the spec `done` (PR body must contain `Closes <SPEC-ID>`).
**Rework reopens the existing implement handoff**: the owner posts the brief as a comment (no @mention), resets any later stage that is already `done` back to `backlog --no-start`, then sets the handoff `todo` — that status change is the wake. Nobody creates a rework issue. After two failed cycles the ticket's owner escalates: a comment on the ticket @mentioning `sq-lead` **first** (that mention is the wake — `blocked` is not terminal and fires no barrier), then `blocked`. **Human PR feedback goes in a comment on the spec issue, not on the pull request** — nothing reads a PR's comments; the leader turns each concrete request into a new fix ticket and moves the spec back to `in_progress` while it is in flight.
**Nothing runs on a timer.** Every leader and owner wake begins by re-checking its own level (`in_review` with a report posted → `done`; `todo`/`in_progress` with no active run → `rerun`; anything moving → leave it). A stall where nothing completes at all is a failure and is recorded as one.
A change tiny by all four tests may run the fast path after the user says yes: one ticket whose description carries `Mode: fast-path` (that line is how its owner knows the shape), stages implement → open PR, no QA and no docs, closed on the owner's own APPROVE plus the PR URL. Human PR feedback becomes a fix ticket; when that ticket is `done` the leader reopens the **Deliver** ticket so the head the human merges has had integration QA, and its owner re-runs integration QA without opening a second PR.
Every issue the lead creates gets label `run-<YYYYMMDD>-<slug>` so runs can be filtered.

## Hard-won facts (verified unless marked)
- Squad assignment/@mention wakes **only the leader**; members run only when assigned/@mentioned. Squad `instructions` go to the leader only. `role` is a roster label.
- **A repository whose tests fail on `main` is outside the capability boundary**, for the same reason as one with no tests: review and QA have no baseline and the squad cannot tell its own regressions from the pre-existing ones. The boundary must be *established by running*, not inferred by reading — the same rule that already applies to a bug's Reproduction. What makes this happen rather than being skipped is that another agent rejects the spec without it (spec check 4), not that the leader is asked nicely.
- **Platform default says delivered → `in_review`, `done` stays human.** Stage barriers only fire on `done`/`cancelled`. Agent instructions outrank the platform workflow ("Instruction Precedence"), but a *skill* does not, so the status override lives in each agent's own `.md`. Leader also self-heals sub-issues stuck in `in_review`.
- Chat (leader) sees repos only if registered: `multica repo add <url>`; then `multica repo checkout <url>` gives a worktree. Daemon clones need credentials (`~/.git-credentials` has the Forgejo entry). Workspace repo list: kv-cli on Forgejo.
- Forgejo reachable by Multica backend as `http://forgejo:3000` (shared docker network `multica_default`); webhook target must be `http://backend:8080/api/webhooks/vcs/<connection-id>`, not the localhost URL the UI shows. Forgejo needs `webhook.ALLOWED_HOST_LIST=*`.
- Timeline entries carry `actor_type` (agent/member) → interventions are measurable; runs carry `usage` (array per model), `is_leader_task`.
- **`attribution.source` is NOT "who started this run"** — it names the human or agent at the root of the causal chain, so it is useless on its own (measured table in `bench/failures.md`). A platform stage barrier reports `delegation` in an agent-built family but `direct_human` in a hand-built one; a person firing a rule by hand reports **`trigger_owner`**. What actually discriminates: `wakeup_system_rule` non-null = a platform rule fired; `attribution.delegated_from_task_id` present = another agent's task caused it; neither = a person (or an `sq-medic` restart, which the scorer pairs with its `**Medic**` comment). `usage` is **summed over every request in a run**, so `cache_read_tokens` = context size x request count and is NOT a context peak: B1's 1,207,032-cache-read run had accumulated only **59,797** tokens of context, re-read ~20 times. `cache_write_tokens` is the context actually accumulated (B1 max 62,953 over 74 runs, leader median 10,631), and is the D-tier metric. The v4 "1.23M context peak" was the same misreading.
- **Platform stage barriers are reliable; v4's missed wake was not a barrier.** Setting a child `done` fires `child_done` on the parent within ~20 s, and `issue update --no-start` suppresses the run on the issue being updated but **not** the parent's barrier. v4's un-woken leader came from an **agent-created** wakeup rule that the platform rate-paused; v6 creates no such rules (v5 families have zero and their barriers fired).
- **A `child_done` barrier wakes the parent issue's assignee even when that is an individual agent, not a squad** (probe F18, 2026-10-17: parent ACHE-144 assigned to `sq-reviewer`, child set `done` 14:04:39 → a `sq-reviewer` run the same second, `wakeup_system_rule: child_done`, `is_leader_task: None`). Only *squad* assignment is leader-only. This is what makes per-level ownership possible; v6 woke the leader on every stage only because every ticket was squad-assigned.
- **Custom properties give a closed, normalized vocabulary — the one guarantee prose cannot** (probe F21). `multica property create --type select` then `issue property set <id> --name Verdict --value "PASS"`: an invented value is rejected with the valid list, a case variant is normalized to the canonical name, and `issue property list <id>` returns `name` + `display` resolved (`issue get` keys them by UUID, so use the list form). Definitions are owner/admin only, so they live in `properties/*.json` and `sync.py` creates them; agents only set values. **Property changes do NOT appear in the timeline**, so a property is the authoritative *final* state and can never count cycles.
- **The platform's duplicate guard is defeated by paraphrase** (probe F20): an identical title is rejected (`Active duplicate issue exists: …; use --allow-duplicate`), but one extra word in the title creates silently — exactly the ACHE-125/127 shape. A guarantee against duplicates has to be semantic ("compare by what the issue is FOR"), which is why it lives in the instruction.
- **`status_changed` timeline entries carry `details.from`/`details.to`**, so v7's rework count is exact: a handoff going `done` → `todo` is one cycle, with no prose parsed. The legacy prose counts (`review_changes_requested`, `qa_fail`) match the phrase anywhere in a comment and over-count when a later comment quotes a verdict (B1: 2 real verdicts counted as 3); they are kept only for pre-v7 comparability.
- **A stage barrier wakes the owner but does NOT promote the next stage** (probe F19, 2026-10-17: stage 1 `done` fired one `child_done` run on the parent while the stage-2 child stayed `backlog` for 75 s). So Multica has no "unblock and let a free worker claim it" model — coordination here is push (wake the owner, the owner promotes), never pull. This is why the squad cannot adopt Claude Code Agent Teams' dependency-unblock-plus-self-claim pattern; it is a platform limit, not a design choice.
- **`multica issue children <id>` returns one entry per stage with `total` and `done` counts** (plus the issues), so the layout is one call — but **never derive *which* stage just finished from those counts**: after any reopen the counts can show two stages complete, and the owner then reads a stale verdict and reworks forever. The barrier's own system comment already says it: `Stage N of this issue is complete — its last sub-issue [ID] … Stage progress — Stage 1: 1/1 done; Stage 2: 0/1 done (next)` (`handler/issue_child_done.go:366` + `stageProgressSummary`). Read the newest comment on the issue that woke you; it also distinguishes a barrier wake from a human comment and from an escalation. Its trailing advice to set the parent `in_review` contradicts this squad's status override, which wins.
- **Terminal means `done` or `cancelled`, and nothing else** (`handler/issue_child_done.go:99`, `isTerminalChildStatus`). `blocked` fires **no** barrier, so `blocked` alone is a permanent stall in a squad with no medic: escalation is an @mention comment first, then `blocked`. The mention wakes the mentioned agent even on an issue it is not assigned (B1: the implementer's report mentioned `sq-lead`, which ran at 12:36:25 on `ACHE-122`).
- **Wake deduplication is per (issue, agent)** (`HasPendingTaskForIssueAndAgent`, same file `:914`, keyed on the reviewed head SHA), so a report that @mentions its owner and the barrier that follows are **two runs on two different issues**: measured 12:36:25 on the child and 12:36:26 on the parent. **18 of B1's 74 runs started within 3 s of a comment** — roughly a quarter of the cost, and in v7 the owner's wake promotes stages, so the duplicate can promote twice. Reports therefore @mention nobody.
- **The barrier closes only when every stage ≤ the completing child's stage is terminal** (`stageBarrierClosed`, same file `:571`), so a stage that completes while a lower stage is still open wakes nobody. Promote one stage (and one ticket) at a time.
- **A parent in `backlog`, `done` or `cancelled`, or assigned to a human, gets no child-done notification at all** (same file `:118`-`:131`). Never leave work running under a parent in one of those states — which is also why a reopened ticket must leave `done` before its children restart.
- **Creating an issue in any status other than `backlog` starts a run on its assignee immediately**, and `issue create` has no `--no-start` (only `issue status`/`issue update` do). Measured: `ACHE-114` created `in_progress` at 12:32:14 started a leader run that logged `squad_leader_evaluated: no_action — "Assignment wake on spec creation; chat run already…"`, while `ACHE-115` created `backlog` at 12:32:25 started nothing and ran only when promoted at 12:32:48. So every issue is created `backlog` and moved afterwards.
- **Reopening a completed stage and completing it again re-fires the barrier** (same probe: child back to `todo`, then `done` again at 14:06:21 → a second `child_done` run within 15 s). So rework can be a status change instead of a new issue. `--stage` groups children into an ordered barrier group and the CLI states the parent assignee is woken only when *every* sub-issue in a stage finishes.
- **Concurrent leader runs are normal and harmless when they are on different issues.** B1 had 12 overlapping `sq-lead` run pairs (`max_concurrent_tasks: 3`), every one of them a spec run overlapping a ticket run during a pipelined handoff; two runs on the *same* issue never overlapped. B1's duplicate rework (`ACHE-127`) was **one run repeating its own create 25 s apart**, not a concurrency race — and the duplicate was acted on, costing a stray commit and an extra rework round (`bench/failures.md` 2026-10-17).
- **A comment on a squad-assigned issue wakes the leader by itself**, so commenting and then `rerun`-ing the same issue wakes it twice, 30 s apart — two leaders on the same state can promote a stage or open a rework twice (found by probe F17-2, fixed in `agents/medic.md`).
- `multica issue wakeup create` needs an explicit `--agent-id` when a person runs it (it defaults to the authenticated *agent*), and event names are dotted (`comment.created`, not `issue_commented`); `multica issue wakeup events` lists them.
- `multica issue runs <id> --active` answers "is an agent working right now", `--siblings` widens it to the issue family. `multica issue rerun <id>` re-enqueues the current assignment and does not depend on wakeup rules (what sq-medic uses); `multica issue wakeup trigger` is the manual fire, and `manual` fires bypass the rate pause (`issue_wakeup.go:1292`).
- The VCS webhook models only `pull_request` and `ci_status` (`vcs_webhook.go:139`); **PR comments never reach Multica through it**, so the PR-comment relay polls the Forgejo API instead (`tools/forgejo-pr-comments.sh`). CI status *is* modelled, so Forgejo Actions would mirror onto the PR without extra wiring.
- Agents push as **`squadbot`** (credential in `~/.git-credentials`, token also in `forgejo/.env` as `FORGEJO_TOKEN`; the admin token is kept as `FORGEJO_ADMIN_TOKEN`). `main` is protected on `kv-cli` and `kv-bugs`: direct push is rejected by the server and only `squadadmin` may merge. Verified for real, not by reading settings.

## Experiment log
1. hello CLI — needed many manual DONE clicks (status policy bug). 2. hello CLI — one nudge to wake the lead. 3. todo CLI + PR on GitHub — zero intervention to PR; merge needed manual status. 4. kv CLI + PR on Forgejo — zero intervention, merge auto-set `done`.

## Rules for working here
- Benchmark runs: never delete feature branches/PRs/issues/labels; one branch per attempt, PRs left open (not merged), `main` untouched.
- Run the squad hands-off when testing; never press status buttons mid-run (it invalidates the run).
- Commit after each config change; scorer records the squads-repo sha.
- Confirm with the user before outward-facing actions (creating repos, pushing to remotes, spending lots of agent runs).
