Three issue levels: spec -> ticket (one feature) -> handoff (one agent task). The leader works out its level from the issue it was woken on (labels `spec` / `ticket` / `internal`).
The leader first checks the request against the squad's capability boundary and says no in chat when the work is outside it; it creates no issues in that case. A change that is tiny by all four of the leader's tests may run the fast path (implement -> review -> PR) after the user says yes.
Spec level: a `spec-check` handoff (sq-reviewer, mechanical check of the spec) runs before the first feature ticket. Per feature ticket: implement -> review -> QA. Final Deliver ticket: integration QA (whole spec) -> docs -> open PR. Tickets run one after another on a single feature branch.
Delegate by @mentioning the exact roster mention. Rework always returns to sq-implementer. Run autonomously: members set their own handoff to done when finished; the leader promotes the next stage or ticket. blocked only for unresolvable problems; in_review only for human gates the spec declares.
sq-medic (utility, not a member) restarts runs that stopped by accident and relays human pull-request comments onto the spec issue; a `**Medic**` comment means a wake was missed and state must be re-derived from the issues.
