Three issue levels: spec -> ticket (one feature) -> handoff (one agent task). **Ownership is per level**: the spec belongs to sq-lead, each ticket belongs to sq-reviewer, each handoff belongs to the agent it is assigned to. A stage barrier wakes the owner of the parent issue, so work moves without anyone being nudged, and the leader is woken once per ticket rather than once per stage.
The leader first runs the repo-intake skill on every repository involved (does it build, do its tests pass on `main`, what is the formatter baseline, is there a conventions file, can the squad push) and checks the request against the squad's capability boundary, saying no in chat when the work is outside it; it creates no issues in that case. A repository whose tests fail on `main` is outside the boundary for the same reason as one with no tests. The spec carries the intake output verbatim and the spec check re-runs the two that matter. One spec is in flight at a time. A change that is tiny by all four of the leader's tests may run the fast path after the user says yes: one ticket marked `Mode: fast-path`, stages implement -> open PR, the owner's own review in the wake between them, no QA and no docs.
Spec level: a `spec-check` handoff (sq-reviewer, mechanical check of the spec) runs before the first feature ticket; then the tickets, one after another on a single feature branch. A feature ticket has two handoffs, implement (sq-implementer) and qa (sq-qa) — the review happens in the owner's own wake, on the ticket. The final Deliver ticket has docs, then integration QA (whole spec), then open PR — docs first, because it commits to the same branch and the head the human merges must be the one integration QA ran.
Rework reopens the existing implement handoff: a comment naming what to fix and what has already been ruled out, then **two** status writes — `backlog`, then `todo`. Only a move out of `backlog` starts a run, so a single `done -> todo` leaves the issue looking correct with nobody working. Nobody creates a rework issue. After two failed cycles the ticket's owner escalates: a comment on the ticket mentioning `sq-lead` in the roster link form **first** (that mention is the wake, because `blocked` fires no barrier), then `blocked`.
Run autonomously: members set their own handoff `done` when finished, owners promote the next stage, and every wake begins by re-checking the level it owns — there is no recovery utility and nothing runs on a timer. `blocked` only for unresolvable problems; `in_review` only on the spec, for the human gate.
Human review comments belong on the spec issue, not on the pull request: nothing reads a pull request's comments.
