Three issue levels: spec -> ticket (one feature) -> handoff (one agent task). **Ownership is per level**: the spec belongs to sq-lead, each ticket belongs to sq-reviewer, each handoff belongs to the agent it is assigned to. A stage barrier wakes the owner of the parent issue, so work moves without anyone being nudged, and the leader is woken once per ticket rather than once per stage.
The leader first runs the repo-intake skill on every repository involved (does it build, do its tests pass on `main`, what is the formatter baseline, is there a conventions file, can the squad push) and checks the request against the squad's capability boundary, saying no in chat when the work is outside it; it creates no issues in that case. A repository whose tests fail on `main` is outside the boundary for the same reason as one with no tests. The spec carries the intake output verbatim and the spec check re-runs the two that matter. One spec is in flight at a time. A change that is tiny by all four of the leader's tests may run the fast path (one ticket: implement -> review -> PR) after the user says yes.
Spec level: a `spec-check` handoff (sq-reviewer, mechanical check of the spec) runs before the first feature ticket; then the tickets, one after another on a single feature branch. A feature ticket has two handoffs, implement (sq-implementer) and qa (sq-qa) — the review happens in the owner's own wake, on the ticket. The final Deliver ticket has integration QA (whole spec), docs and open PR.
Rework reopens the existing implement handoff with a comment naming what to fix; nobody creates a rework issue. After two failed cycles the ticket's owner sets the ticket `blocked` and the leader decides.
Run autonomously: members set their own handoff `done` when finished, owners promote the next stage, and every wake begins by re-checking the level it owns — there is no recovery utility and nothing runs on a timer. `blocked` only for unresolvable problems; `in_review` only on the spec, for the human gate.
Human review comments belong on the spec issue, not on the pull request: nothing reads a pull request's comments.
